# ABHEDYA Evaluation and Claims Policy

## Why this document exists

ABHEDYA contains multiple ML components, online adaptation logic, detection telemetry and research artifacts. This document defines how performance claims should be interpreted and what evidence is required before stronger claims are made.

The goal is reproducibility and technical honesty rather than marketing language.

## Implemented decision pipeline

The current hybrid decision layer combines three outputs:

```text
final_score = 0.4 * xgb_score + 0.4 * cnn_score + 0.2 * dqn_score
```

The resulting score is compared with a dynamic threshold loaded from SQLite, with a fallback of `0.65` when configuration is unavailable.

These values are behavior-sensitive contracts and are protected by lightweight CI regression checks.

## Model roles

### XGBoost

The XGBoost component consumes aligned tabular traffic features and contributes a probability-derived score to the hybrid decision.

### CNN-LSTM

The CNN-LSTM component contributes a learned traffic-pattern score using its expected feature representation.

### DQN

The DQN component maps its predicted label to an action class. In the hybrid score, the current decision layer converts the DQN action to a binary contribution before applying the 0.2 ensemble weight.

## Online DQN adaptation

`backend/dqn_retrain.py` can retrain a DQN policy using recent detection records from SQLite.

Important limitations of the current implementation:

- recent stored detections are reused as the adaptation dataset;
- labels may be derived from an existing prediction or from score-based pseudo-label rules;
- the reported retraining `accuracy` is calculated against samples from the same adaptation data rather than an independent hold-out set;
- therefore this value is a **training/adaptation diagnostic**, not a generalization benchmark.

A recruiter, reviewer or researcher should not interpret that value as independent model accuracy.

## Explanation layer

The current `xai_explanation` value is generated by a deterministic rule-based feature-highlighting function.

It is **not** a SHAP or LIME attribution implementation.

If SHAP/LIME is added later, that implementation should be evaluated separately for computational cost, fidelity and stability rather than simply changing the documentation label.

## Evidence levels

ABHEDYA documentation should use the following distinction.

### Implemented

A feature is present in source code and can be traced to a concrete execution path.

Examples include:

- hybrid XGBoost/CNN-LSTM/DQN scoring;
- Kafka prediction/honeypot topics;
- dynamic threshold retrieval;
- HMAC signing of detection metadata;
- honeypot routing and event logging.

### Demonstrated

A feature has been executed in a controlled environment and there is reproducible evidence showing the behavior.

Evidence should include the command/configuration used, input conditions and resulting output.

### Experimentally evaluated

A quantitative claim has been measured using a documented dataset, split, metric definition and evaluation procedure.

### Proposed

The design or documentation describes a future capability that is not yet implemented or independently evaluated.

Claims should never silently move between these categories.

## Required protocol for independent model evaluation

A strong future evaluation should include the following steps.

### 1. Freeze the dataset

Record:

- dataset name/version;
- source and license;
- total samples;
- class distribution;
- feature schema;
- preprocessing steps;
- duplicate-removal policy;
- train/validation/test split identifiers or deterministic seed.

The final test set must remain untouched during model selection and threshold tuning.

### 2. Evaluate each model independently

For XGBoost, CNN-LSTM and DQN, report metrics separately before reporting ensemble performance.

At minimum:

- accuracy where class balance makes it meaningful;
- macro and weighted precision;
- macro and weighted recall;
- macro and weighted F1;
- per-class precision/recall/F1;
- confusion matrix;
- false-positive rate;
- false-negative rate.

For imbalanced intrusion data, PR-AUC or class-specific recall may be more informative than overall accuracy.

### 3. Evaluate the ensemble

Report the hybrid pipeline using the fixed weights and threshold that were actually used.

The evaluation should include:

- final-score distribution;
- threshold sensitivity;
- false-positive/false-negative trade-off;
- agreement/disagreement between component models;
- comparison against the strongest single model.

### 4. Perform ablation tests

Useful ablations include:

- XGBoost only;
- CNN-LSTM only;
- DQN action only;
- XGBoost + CNN-LSTM;
- full 0.4/0.4/0.2 ensemble;
- fixed threshold versus configured threshold.

This shows whether the hybrid design adds measurable value rather than assuming that additional models are automatically beneficial.

### 5. Measure runtime behavior

Latency should be measured on a specified machine/environment and reported as a distribution rather than a single best-case number.

Recommended measurements:

- packet/feature-processing latency;
- per-model inference latency;
- end-to-end decision latency;
- Kafka transport overhead where included;
- p50, p95 and p99 latency;
- throughput under controlled load;
- memory and CPU use during sustained operation.

### 6. Test degraded modes

The current hybrid layer contains fallbacks when model calls fail. Evaluation should explicitly test:

- missing model artifact;
- model inference exception;
- Kafka unavailable;
- SQLite unavailable/locked;
- invalid telemetry schema;
- unavailable dynamic-threshold configuration.

A fallback should be documented as degraded operation, not silently counted as successful model inference.

## Security evaluation

Beyond ML metrics, ABHEDYA should be evaluated as a security system.

Recommended controlled tests include:

- brute-force login attempts;
- port scanning;
- SQL-injection-like traffic patterns;
- DDoS-like traffic;
- malformed Kafka messages;
- unauthorized administrative requests;
- log-signature tampering;
- honeypot redirection and isolation;
- repeated/replayed events;
- model-artifact replacement in a disposable lab copy.

Every test should identify the expected behavior before execution.

## Reproducible result template

Future benchmark reports should contain a compact block similar to:

```text
Dataset/version:
Split strategy:
Random seed:
Feature pipeline commit:
Model artifact hash:
Threshold:
Ensemble weights:
Hardware:
Software versions:

Per-model metrics:
Ensemble metrics:
FPR / FNR:
Latency p50 / p95 / p99:
Known limitations:
```

## What should not be claimed yet

Until independent evidence is added to the repository, avoid claims such as:

- zero-breach resilience;
- guaranteed attack prevention;
- enterprise-ready autonomous defense;
- independently validated real-time accuracy;
- SHAP/LIME explainability;
- production-grade online reinforcement learning;
- immunity to adversarial or zero-day attacks.

The implemented system is already substantial without those claims. Precise language makes the project stronger under technical review.
